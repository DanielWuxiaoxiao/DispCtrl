# X576 雷达系统内部通信协议（v5.0，2025-12-11）

> 本文档为显控（DispCtrl）软件与内部各子系统的通信协议全集。小端、1 字节对齐，统一帧头 0xFA55FA55 / 帧尾 0x55FA55FA，校验为 1 字节 XOR。

## 文档控制与变更记录

- 会签：西安电子科技大学
- 版本记录：
  - 1.0 (2025/08/18，张华斌)：初版
  - 2.0 (2025/09/02，张华斌)：DBT 航迹上报批号改为 2 字节（2.2.5.1）
  - 3.0 (2025/09/05，张华斌)：修改资源调度→显控伺服回送（2.2.7.1）
  - 4.0 (2025/09/18，张哈斌)：跟踪调度请求时间与控制表一致（2.2.6.1）；BIT 上报增加偏航与子阵电源 BIT（2.2.7.2）
  - 5.0 (2025/12/11，张华斌)：控制表 512B 与外部协议一致；四面阵启动规则（2.2.1.1）；新增目标识别软件运行状态上报（2.2.11）
  - 5.1 (2025/12/25，显控)：补充显控↔外部雷控链路占位收发（系统控制 512B/回执 64B，伺服控制 32B/回执 32B），默认 IP/端口/ID 写入 config.toml

#### 2.2.1.8 雷达位置信息控制 (0xAA08)

显控手动下发至资源调度，沿用既有帧头/校验/UDP端点。以下为负载内从0起算的字节偏移，小端、1字节对齐，总长142B。

| 偏移 | 字段 | 类型 | 量化 |
| --- | --- | --- | --- |
| 0 | 信息编号 | uint16 | 0xAA08 |
| 2+31×ID | 雷达ID | uint8 | 固定0、1、2、3 |
| 3+31×ID | 纬度 | int64 | 1e-9° |
| 11+31×ID | 经度 | int64 | 1e-9° |
| 19+31×ID | 高程 | int32 | 0.01m |
| 23+31×ID | 航向 | uint32 | 0.001° |
| 27+31×ID | 倾角 | int32 | 0.001° |
| 31+31×ID | 横滚 | int16 | 0.01° |
| 126 | 预留 | 16B | 全零 |

V6.4：多面阵下发按钮打开四行实时窗口，未收到有效报告时按配置及ID×90°初始化；之后每ID经纬高/姿态取最近10个有效值平滑（航向为圆周平均）。未锁定行只读，每200ms刷新；只有锁定后可编辑。经纬高编辑同步其他已锁定行，姿态独立。高程-1000～5000m，经纬度/姿态按协议范围校验，非有限或空值整表拒绝。只有“确定下发”才按142B结构提交请求，未锁定行使用当前有效参考，锁定行使用编辑值并更新冻结参考，16B预留清零；无设备确认帧，不声称设备已应用。不自动保存到config.toml。

## 2026-07-14 protocol update

- `0xDD01` point reports now use the documented 56-byte point record: the last 8 bytes are `targetConfidence` (`float`) and `targetRecResult` (`uint`). The frame-level `radarId` is in the range `0..3` and is copied into `PointInfo::radarId`.
- Single-panel `0xDE02`: 39B legacy payload. Multi-panel V6.3: 103B payload preserving that entire prefix, followed by LLA/attitude and 34 reserved bytes. The startup panel count selects the layout; 58B is obsolete and rejected. See section 2.2.7.2. Health/scan consumers retain the normalized 39B status model.
- `0xEE01`, `0xEE02`, and `0xEE03` track reports were kept in the existing layout: `mesID` + `trackNum` + `N * trackInfo`. The field sum of `trackInfo` is 61 bytes, although the 2026-07-14 table says 58 bytes. These tables do not define a radar/array ID, so track frames cannot be separated by radar ID until that field position and size are specified by the protocol owner. Legacy track decoding therefore remains unchanged and uses radar ID 0 internally.
- The 2026-07-03 external-control document adds fields inside the existing opaque 512-byte system-control table. `ExternalSystemControl512` remains a pass-through buffer; no external frame-size change is required in the display controller.
- `Basic/Protocol.h` contains size assertions for the byte-level structures. Invalid DD01 radar IDs are logged, and DD01/DE02 receive logs include the radar ID for field troubleshooting.
- Health management now keeps four independent `BITReport` caches and presents four tabs (`radarId` 0..3). Software status remains shared; hardware BIT, temperature, yaw, scan angle, and last-report time are updated per array.

### AA09 跟踪数据率调整（2026-10-30）

显控向资源调度发送，小端1字节对齐，负载5B：偏移0 uint16信息编号0xAA09，偏移2 uint16航迹批号，偏移4 uint8数据率Hz（默认2，上限100）。当前UI允许1～100整数Hz，协议未定义0的停发含义，因此不发送0。沿用资源调度UDP通道/包头/通信计数/校验，完整封装24B。普通航迹标签/点右键及普通/无人机航迹表右键均可选择“调整跟踪数据率”；取消不发送。仅记录下发请求，不假定设备已执行，也不修改显控本地航迹接收/绘制刷新频率；未扩展到TBD或协同航迹。
