# 开窗后退出排查（2026-10-22）

## 已证实的崩溃

本机 Windows Application 事件记录：2026-10-22 10:56:32、11:00:13、11:39:19，均为 `E:/DPRelease/DispCtrl.exe`、异常 `0xC0000005`、RVA `0xDFF3E`。使用 11:39 对应的本地转储 `DispCtrl.exe.20168.dmp`、匹配 EXE 和同批 COFF 对象离线核对：故障指令读取 `[rdx+0xD0]`，`rdx=0`，即已析构覆盖层的 `ui=nullptr`。

转储栈中的返回地址与对应函数逐一匹配：

| RVA | 位置 |
|---|---|
| `0x90544` / `0x8FDBC` | `CommandControlModule` 删除析构 / 析构中调用停止网络 |
| `0xA0E7B` / `0x14ED3` | `stopNetwork()` 发出 `readyChanged(false)` / Qt信号激活 |
| `0xEF41A` / `0xDFF3E` | `setCommandControlModule()` 重排布局 / 访问 `ui->btnDataProcess` |

原因：主窗口删除子对象时先销毁覆盖层，再销毁总控模块；原 `readyChanged` 回调以主窗口为接收上下文，主窗口仍活着，因而回调继续访问已销毁的覆盖层。总控 `enabled=false` 仍创建模块，析构原先也无条件通知，因此关闭配置不能规避。

修复：回调上下文及捕获对象改为覆盖层；模块析构停止网络时不再发就绪通知，但保持记录封口/flush和线程退出；覆盖层析构先断开总控信号、同步销毁健康/存储子窗口，保证其销毁回调访问的计时器和数组仍有效。未改变四面阵数据、状态过滤、通信或图形配置。

## 尚不能下结论的部分

上述证据确认的是**退出销毁期崩溃**，不单独证明“打开窗口为何开始退出”。用户提供的日志有 `WebGL: too many errors`、非法UDP帧和GUI积压后成批处理迹象，均不足以直接认定为此次访问冲突的起点；也未发现健康页 0～3 索引越界证据。
