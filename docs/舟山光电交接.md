# 舟山光电配置与联调交接

适用版本 V8.5.0。显控提供 TCP 光电目指和 HTTP 平台航迹上报两条通路。两条通路默认关闭，各自配置、选批、停止和记录日志，可同时运行。

| 通路 | 网络角色 | 操作入口 | 成功依据 |
| --- | --- | --- | --- |
| TCP 光电目指 | 显控监听，光电主动连入 | P 显「光电(F6)」、普通航迹右键、「光电目指状态」 | 核对匹配回传及其处理结果 |
| HTTP 平台上报 | 显控主动向平台发起 POST | 「参数设置 → 平台航迹上报」、普通航迹右键 | HTTP 2xx 且响应 JSON 的数字 `code` 为 `200` |

## 1. 部署配置

以启动日志 `Config file path resolved to:` 显示的路径为准，修改运行实例实际加载的 `config.toml`，保存后重启。下面的地址为示例，部署时使用现场分配的网卡、对端和服务端点。已有同名段时直接改对应键。

```toml
[zhoushan_optical]
enabled = true
local_ip = "192.0.2.10"
peer_ip = "192.0.2.20"
listen_port = 9010
sender_id = 1100
receiver_id = 3101
indication_type = 1
time_basis = "local"
report_interval_ms = 1000
response_timeout_ms = 3000
track_timeout_ms = 10000
max_tracks = 1024
log_enabled = true
log_payload_enabled = false
log_interval_ms = 5000

[radar_track_api]
enabled = true
endpoint = "https://platform.example.com/api/gateway/radar_track/receive"
token_env = "DISPCTRL_RADAR_TRACK_API_TOKEN"
api_token = ""
model = "RADAR"
track_id_prefix = "SITE-"
auto_report = false
report_interval_ms = 1000
request_interval_ms = 100
response_timeout_ms = 3000
track_timeout_ms = 10000
max_tracks = 1024
log_enabled = true
log_payload_enabled = false
log_interval_ms = 5000
```

- TCP 的 `local_ip` 必须配置在显控本机网卡上。光电连接该 IP 和 `listen_port`，显控只接受来自 `peer_ip` 的一个活动连接，光电源端口可变。端口、发送／接收设备 ID 和 `time_basis`（`local` 或 `utc`）需双方一致。
- 舟山 TCP、光电 V2、9009 激光共用光电操作入口。舟山 TCP 独占部署时将 `[photoelectric_v2].enabled` 和 `[laser].enabled` 设为 `false`。同时开启时优先级为舟山 TCP、光电 V2、9009 激光。HTTP 平台上报可与任一已启用的光电协议并行。
- HTTP 令牌优先读取进程可见的 `token_env`，其次读取本机 `api_token`。Git 与发布模板中的 `api_token` 保持空值。缺少令牌时窗口可用于诊断，HTTP 不发送。`auto_report = false` 时，启动后由操作员手动选批或开启自动上报。

## 2. TCP 光电目指

1. 在健康管理或「光电目指状态」确认本机地址、对端 IP 和 TCP 连接。ICMP 可达与 TCP 已连接分别核对。
2. 确认显控已有有效雷达原点和未过期的普通航迹。按 F6 输入批号，或在 P 显该航迹上右键下发。TCP 同时只服务一批，选新批后旧批停止继续发。
3. `indication_type = 1` 为持续目标提示。每次最多一条待回执，请求结束后按间隔取同批最新点。对端回传区分「已接收并处理」与「已接收但忽略」。`indication_type = 2` 为单次确认请求，每次人工操作发一条，结果区分「不能确认」「是目标」「不是目标」。超时或断线后重新人工发起确认。
4. 在「光电目指状态」对照最近下发、当前批次回传和上一批次回传。确认批号、类型、时间和结果匹配。当前批切换时保留上一不同批次作为对照。手动停止、消批或航迹过期会停止后续发送，已进入 TCP 的请求仍可能在对端执行。

接入范围为光电协议第 6 节目标指示及响应。TCP 请求和回传均为 48 字节，在线类型分别为 `04 00`、`04 01`。排查回传失配时核对双方 ID、当前会话、批号、类型和时间。持续提示还要求对端原样回显请求坐标。单次确认允许对端返回修正坐标，显控仅展示。线协议和校验范围见 [舟山光电目指接入说明](舟山光电目指接入说明.md)。

## 3. HTTP 平台航迹上报

1. 在窗口输入批号，或在 P 显普通航迹的右键菜单启用该批平台上报。可同时手动选择多批，各批持续上报最新点。
2. 勾选「自动上报全部无人机航迹」后，模块根据普通航迹最新识别结果上报全部无人机（`targetRecResult = 1`）。手动选批可以选其他识别类别。自动与手动互相独立，停止某批手动上报后，若该批仍命中自动条件，它会继续上报。需要全部停止时点击「停止全部平台上报」。运行期间切换不写回 `auto_report`。
3. 对照窗口的请求数、平台确认数与最近结果。平台返回 2xx 且 JSON 数字 `code = 200` 才计为确认。请求超时后结果未知，已发送的请求无法撤回。

请求使用 `X-Api-Token`，每次 POST 一个 JSON 对象。经纬度为 WGS84 度，`altitude` 是海拔米，`timestamp` 是显控收到最新有效样本时的 UTC 毫秒。`speed` 取原始航迹空间速度 `spaceVel`（m/s）。`heading` 由同批有效连续位置推算，真北 0°、正东 90°，顺时针递增。缺少可靠运动信息时省略对应字段。`trackId` 由配置前缀、批号和缓存生命周期标识组成，消批、过期或重启后重新生成。

两条通路都使用普通航迹最新有效点，检测点、TBD、协同和离线回放不作为上报输入。V8.5.0 中，两条通路都从 Controller 接收显控统一参考经纬高，并以有效的 `[radar]` 原点作为启动备用。转换使用航迹的距离、方位和俯仰，海拔取原点海拔加目标垂直分量。

HTTP 全局最多一条请求在途，按批轮转，单批间隔会随批数和响应耗时增加。消批或超时清除该批缓存与手动选批。平台侧类别映射采用服务默认值，验证非无人机手动选批时需核对平台展示口径。报文字段和节拍细节见 [平台 HTTP 航迹上报](平台HTTP航迹上报.md)。

## 4. 排查和验收

| 现象 | 核对项 |
| --- | --- |
| 入口不出现 | 实际配置文件、模块 `enabled`、是否重启。TCP 同时核对光电协议优先级。 |
| TCP 无连接 | 本机网卡地址、监听端口和防火墙，光电是否主动连入，实际源 IP 是否等于 `peer_ip`。 |
| 已连接或已选批但没有数据 | 航迹是否为普通实时航迹并仍未过期，批号和原点是否有效。自动 HTTP 还需核对最新识别结果。 |
| TCP 已入队但无业务结果 | 查对应批次的回传、超时和失配日志，核对 ID、帧类型和回显坐标。 |
| HTTP 已调度但没有确认 | 查 `ERROR` 的 HTTP/API 状态码和超时信息，核对端点、鉴权和平台响应。 |

TCP 搜索 `[ZS-OPT]`，HTTP 搜索 `[TRACK-API]`。两段的 `log_enabled` 分别控制本通路的文件与界面日志，关闭日志时通信和状态窗口仍工作。临时开启 `log_payload_enabled` 可查看 TCP HEX 或 HTTP 发送 JSON，输出仍受 `log_interval_ms` 限制。HTTP 日志不记录令牌和请求头。文件日志同时受 `[system].log_level` 控制，调试使用 `INFO` 或 `DEBUG`。文件为进程工作目录下的 `disp_ctrl_log_0.txt` 至 `disp_ctrl_log_4.txt`，写入失败时回退系统临时目录。

接手后可用一批有稳定更新的测试航迹验证 TCP 的下发和回传，再用两批普通航迹验证 HTTP 手动上报、无人机自动上报和全部停止。记录显控版本、批号和对端业务结果。真实光电连接和平台鉴权以现场联调记录为准。
