# 平台 HTTP 航迹上报（V8.4.0）

此通路对应用户提供的 `radar_track-api-doc.md`，与现有光电 TCP 目标指示分别控制，可以同时使用。配置段为 `[radar_track_api]`；默认关闭。两种主题及实时换肤使用相同业务对象，切换主题保留手动选批、自动模式和网络状态。

## 启用和操作

1. 在实际运行目录的 `config.toml` 中设置 `radar_track_api.enabled = true`。
2. 设置运行进程可见的环境变量 `DISPCTRL_RADAR_TRACK_API_TOKEN`，或在本机 `api_token` 中填入平台令牌。环境变量优先。模板保持空值，不把实际令牌提交到 Git。
3. 启动软件，在「参数设置 → 平台航迹上报」打开控制窗口；也可以右键 P 显普通航迹，开启/停止该批手动持续上报，或打开设置窗口。
4. 控制窗口可按批号加入多个手动目标；独立的自动开关持续上报全部 `targetRecResult=1` 的无人机。停止某批手动上报不关闭自动模式；需完全停止时使用「停止全部平台上报」。窗口中的自动开关仅改变当前运行状态，下次启动由 `auto_report` 决定。

关闭 `enabled` 时不创建模块、HTTP 线程、计时器和 UI 入口。缺少有效 Token 时保留启用后的配置诊断窗口，但不创建 HTTP 工作线程、不能开始上报。修改端点、令牌或配置默认值需重启；换肤无需重启。

## HTTP 契约

- 方法和地址：`POST http://api.csscuss3d.com/api/gateway/radar_track/receive`。
- 请求头：`Content-Type: application/json`、`X-Api-Token: 本机令牌`。
- 请求体：单个 JSON 对象，一条航迹的最新点；坐标和时间为 JSON 数字。
- 成功：HTTP 状态 2xx，且响应 JSON 对象中的数字 `code` 等于 200。HTTP 成功、网络可连接、本机排队均不能单独代表平台接收成功。
- 超时只说明结果未知；平台可能已收到请求。本接口没有幂等键、撤回、删除、取消、心跳或终止 API，不自行添加。
- 不自动跟随重定向。端点须为无用户名/密码、查询参数和片段的 HTTP/HTTPS URL；若平台迁移地址，修改配置后重启。

| 字段 | 来源和单位 |
| --- | --- |
| `trackId` | `track_id_prefix` + 批号 + 本次航迹缓存生命周期 UUID；同一生命周期内稳定，不同批/重启/消批后重建区分 |
| `longitude` | WGS84 经度，度 |
| `latitude` | WGS84 纬度，度 |
| `altitude` | 雷达有效原点海拔 + 距离 × sin(俯仰角)，米；不直接使用相对高度字段 |
| `timestamp` | 显控 GUI 业务回调收到最新有效样本时的 UTC 毫秒，不是雷达报文内源时标 |
| `model` | 配置值，默认 `RADAR` |
| `speed` | 原始 EE01 报文 `trackInfo.spaceVel`，空间速度大小，m/s；不取显示模型中的径向速度 |
| `heading` | 同批连续位置的水平运动航向：真北0°、正东90°、正南180°、正西270°，顺时针、范围[0,360)，度 |

本轮用户在初版后明确补充：**`speed` 是空间速度，`heading` 是目标运动方向相对真北的角度**；据此补齐这两个字段，并覆盖原 MD 中将 `speed` 描述为水平速度的口径。速度直接使用同一原始样本的 `spaceVel`，有限且非负时发送，0是有效值；不对负值取绝对值。缺失、NaN、无穷或负值时省略。`vel` 是径向速度，P 显方位是目标位置方向，均不替代这两个字段。

航向采用水平投影，通过 `atan2(东向位置增量, 北向位置增量)` 计算，无额外偏航叠加。原始 EE01 没有运动航向字段，因此这是连续位置的推算值。仅用同批、有效原点、有效且递增的 `UTCtime/nsecond` 样本配对；第一点、水平位移不超过1mm、时标缺失/无效或样本间隔超过航迹超时限时省略。仅垂直运动不产生水平航向。雷达原点变化后重建方向基点；消批/失效后新生命周期也从首点开始。乱序和相同时标但位置冲突的点不覆盖本 HTTP 缓存；同点重复帧保留已计算航向。未添加航向平滑或运动滤波，位置噪声可能影响逐点推算结果。

独立模块订阅 `normalTrackFrameReady`，按14B帧头+4B航迹头+61B记录读取小端空间速度与源时标；当前帧最多4096条元数据，按帧内顺序与随后发布的 `PointInfo` 精确配对，不按批号覆盖重复记录。整帧用完或不匹配时不借用旧样本元数据。本地生成或缺少原始帧的点仍可走原有选批链路，但不伪造空间速度/航向。未修改 `PointInfo`、普通航迹接收解析或既有显示字段。

经纬高使用 Controller 发布的统一有效雷达原点，启动阶段以有效 `[radar]` 经纬高备用。复用现有 `Wgs84Coordinate` 局地切平面近似：0°正北、90°正东，距离米、方位和俯仰度，不追加偏航旋转。本轮不改变电磁计算口径。非法/非有限坐标不编码发送。

只接入 `Controller::traInfoProcess` 的普通航迹，排除检测点、TBD、协同和 `statMethod=250` 离线数据。`statMethod=2` 消批和超时均移除手动选择。自动模式按最新点识别决定是否调度；手动允许指定其他识别结果。平台映射的 `device=7`、`aircraftState="0"` 为服务端默认值，当前没有对应上报字段，因此手动选择的其他类别也会被平台按无人机默认值处理；如需上传类别，须先约定平台映射。

## 时序、容量与诊断

每批仅缓存最新有效点，最大缓存 `max_tracks`（1～4096，默认1024）；超限拒绝新增批号，失效清理后释放容量。`track_timeout_ms` 按显控业务回调接收的单调时间计时，不受系统校时影响。

独立线程执行异步 HTTP；全局最多1条请求在途，按批号轮转。`report_interval_ms`（默认1000）是每批最小间隔，`request_interval_ms`（默认100）是全局最小间隔，实际频率还取决于平台响应时间和目标数。例如100ms的全局间隔上限约10条/秒，多目标轮询可能使每批间隔超过1秒。没有逐点请求队列，不积压/补发历史坐标；停止或更新原点使尚未发出的相关旧请求失效，已发请求不能撤回。

`response_timeout_ms` 默认3000；失败至少等待一个每批间隔再尝试其他最新点，避免快速错误循环。响应最多64KiB。窗口显示本机调度请求数、平台确认数、未确认数和最近结果；已取消任务的迟到结果不作为当前任务确认。日志带 `[TRACK-API]` 前缀且限频，不记录 Token、请求头或可能回显敏感信息的服务端自由文本。

## 调试日志配置

在 `[radar_track_api]` 中配置 `log_enabled=true`（默认），控制本通路文件和界面日志；关闭不影响请求、自动上报或窗口状态。`log_payload_enabled=false` 默认只记录发送批号/字节数和本机调度状态；改为true可记录发送的JSON正文。始终不打印Token、请求头或服务端自由文本。`log_interval_ms=5000` 控制TX、成功响应、失败及状态各类别最短日志间隔，范围1000～60000ms，错误不会被TX日志占用限频槽。

用`[TRACK-API]`搜索：`CONFIG`是端点/节拍/配置问题，`SELECT`/`STOP`/`AUTO`是手动和自动操作，`TX`只是本机调度，`RESPONSE`表示HTTP与API均成功，`ERROR`记录失败HTTP/API码、超时或响应超限。与 `[zhoushan_optical]` 的日志开关独立，改配置后重启生效。

文件日志还受 `[system].log_level` 控制，调试用`INFO`或`DEBUG`；文件为进程当前工作目录下的`disp_ctrl_log_0.txt`～`disp_ctrl_log_4.txt`，无法写入时回退系统临时目录。界面日志可在主窗口日志区查看。

## 验证范围

`tests/radartrackapi_test.cpp` 提供字段/单位、可选字段省略、原始空间速度字节/采样关联、四个真北航向、首点/静止/垂直/乱序/无效时标、同帧重复批号、原点变更、运动字段HTTP实收、手动/自动独立、最新点有界缓存、消批/超时/批号复用、单请求在途、取消、HTTP/API失败、响应超限、超时及双主题窗口生命周期测试。网络测试只连接本机回环模拟服务并使用虚构令牌。CMake 的 `DISPCTRL_BUILD_TESTS` 中注册 `radar_track_api_test`。

不在开发验证中调用实际平台。真实平台鉴权、映射和轨迹展示须在部署环境联调，完整显控构建和现场验收与这些独立测试区分。
